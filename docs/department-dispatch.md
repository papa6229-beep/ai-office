# 대표·실장·부서의 업무 배정과 보고

2026-10-29 확장: 등록 부서창의 실제 직접 지시도 같은 원장/이벤트/본부 inbox/Notion outbox를 사용한다. 정상 입력 delta와 기존 idle 보고는 같은 완료를 중복 전달하지 않는다. 조회·이전 담당 후보·현재 권한의 비동기 배정은 `docs/department-work-loop.md`와 `department_runtime.py`를 따른다. 과거 완료 이력은 새 권한이 아니다.

태준님은 대표, 운영본부의 에이메스는 실장 겸 대표 대리인이다. 현재 사용자 요청을 읽고 적절한 부서에 구체적인 업무를 배정한다. 실장의 1차 처리는 배정 접수까지이며, 부서가 실행하는 동안 본부 채팅을 붙잡고 기다리지 않는다. 완료 후 실장이 결과를 취합하여 대표에게 설명하고 함께 점검한다.

## 실제 배정

1. `department_manager.snapshot(office.db)`에서 실제 팀·연결 요원을 확인한다. 기획/디자인/개발은 기존 채팅을 사용한다. 새 창·새 모델을 임의로 만들지 않는다.
2. 업무명, 현재 맡기는 범위, 완료조건과 필요한 자료 위치를 간단히 정한다. 현재 요청에 없는 외부 발신·상업 데이터 변경 등의 권한을 지침에서 만들어내지 않는다.
3. 프로젝트 Python에서 `department_tasks.assign(DB, payload)`을 한 번 호출한다. 필수 payload는 `team_id`, `title`, `instruction`, `source_request_id`(현재 AI OFFICE 요청의 32자리 ID)다. 연결 요원이 여러 명이면 `agent_id`를 명시한다. 같은 요청·부서·업무명은 기본 배정번호가 같아 중복 접수되지 않는다. 같은 업무를 세부 과정마다 다시 배정하지 않는다.
4. 반환된 배정번호/실제 상태로 접수 사실만 알린다. queued는 전달 완료가 아니다. 작업 진행·부서 응답·실장 보고는 부서관리 → 배정업무에서 확인할 수 있다.

`department_tasks.start(DB)`는 앱 시작 시 한 번 실행된다. 코드가 접수된 업무만 기존 부서 대화에 전달하고 고유 요청표식과 실제 턴 상태로 결과를 확인한다. 결과가 없는 유휴 시에는 모델이나 native 대화를 호출하지 않는다. 연결 실패는 보존·재조회하며 불확실한 전달을 자동 재전송하지 않는다. 배정된 요원이 다른 일을 하고 있으면 전달을 기다린다. 요원별 동시 배정은 한 건이며 다른 요원들은 독립적으로 실행할 수 있다.

## 완료보고

부서의 완료/실패/중단 응답은 업무별로 저장된다. 이는 부서가 제출한 결과이며 실장이나 사용자의 독립 검증 성공으로 간주하지 않는다. 본부가 다른 일을 하는 동안에는 보고를 보관하고 본부가 비었을 때 기존 본부 대화로 전달한다. 한 번에 하나의 보고만 본부에서 정리한다. 본부 최종 답변을 코드가 오피스에 표시한 뒤 대표 보고 완료로 기록한다. 자동 보고를 새 사용자 권한이나 새 업무 지시로 취급하지 않는다.

서버 재시작 후 미완료 업무를 다시 조회한다. 전달 중 끊긴 업무/보고는 고유 표식으로 수신 여부를 확인하며 같은 효과를 임의로 반복하지 않는다. 전달 불명은 배정업무에 표시하며 사용자가 원본 대화를 확인할 수 있다. 승인·입력 요청은 원래 Codex 창에서 처리해야 하며 이 실행기가 자동 승인하지 않는다.

## 범위

부서별 스킬/상세 운영정책/새 팀 구성은 차차 정한다. 업무 해석·배정 판단과 최종 보고는 AI, 저장·전달·진행 관찰은 코드가 맡는다. 코드 폴링이 AI 모델 사용량을 쓰는 것은 아니며, 부서 업무와 실장의 최종 정리에는 기존 선택 모델의 사용량이 발생한다.

## 업무일지 연결 (2026-10-26)

실제 배정된 업무만 `department_journal`에 기록한다. 단순 질문·조회·잡담은 카드나 Notion 페이지로 만들지 않는다. 배정 저장과 같은 트랜잭션의 hook이 의미 있는 상태·제출 결과·실장 보고를 남기며 반복 폴링은 중복 이벤트를 만들지 않는다. 기존 업무는 실제 created/sent_at과 현재 저장된 응답만 복원한다.

실장은 배정하는 기존 턴과 완료보고하는 기존 턴에서 `docs/department-journal.md`의 pending → 공식 Notion fetch/update/fetch → acknowledge 절차를 수행한다. 본부 자료와 새 배정/완료보고 prompt에 해당 안내가 포함된다. 기록을 위한 별도 AI 호출이나 로컬 토큰은 만들지 않는다. 본부 최종 답변 이후에야 코드가 확인하는 대표보고 이벤트는 다음 기존 업무 턴까지 대기할 수 있다. 노션 반영 대기를 업무 완료나 동기화 완료로 표현하지 않는다. 공식 승인 검토가 쓰기를 거절하면 우회하거나 성공 영수증을 만들지 말고 미반영 사유를 보존한다.

## 본부 신속 배정과 기존 화면 의도 보존 (2026-10-26)

태준님이 본부에 직접 수행을 맡긴 업무 외에는 본부가 필요한 자료·기존 구현·완료 기준을 해당 팀에 신속히 전달하고, 접수/전달 상태만 짧게 알린 뒤 턴을 끝내 대화 가능한 대기 상태로 돌아간다. 부서 작업 완료를 기다리며 본부 채팅을 점유하거나 재조사·대리 구현·반복 상태 조회를 계속하지 않는다. 완료보고는 기존 코드 연결로 받아 짧게 정리한다. 일지의 외부 반영은 배정을 지연시키지 않으며 다음 적절한 기존 보고 턴에 묶을 수 있다.
배정 전에는 사용자 용어가 가리키는 기존 화면·기능을 연결하고 원하는 결과와 유지할 범위를 명시한다. 기존 기능의 확장/통합 요청을 새 대체 기능 개발로 임의 해석하지 않는다. 다른 결과가 생길 정도로 모호하면 짧게 확인한다.
2026-10-26 태준님 정정: 통합메신저 창은 일전에 구현한 PC 메신저 원본 앱 화면을 에이메스 안에서 미러링처럼 보여주고 직접 입력하는 기존 팝업을 뜻한다. 별도 수집 메시지 목록/새 채팅 UI를 그 대체물로 만들라는 뜻이 아니다. 태준님이 이미 개발팀에 직접 수정 지시했으므로 본부가 같은 수정 지시를 중복 배정하거나 그 작업에 개입하지 않는다. 개발팀의 새 지시/결과는 해당 대화의 실제 기록을 따른다.

## 스킬 도입·운영 확인의 실장 책임 (2026-10-26)

실장은 승인된 도구/스킬 도입 업무를 설치로 끝내지 않는다. 대상팀의 실제 연결·스킬 발견 가능 여부, 어떤 업무에 쓸지의 선택 기준, 필요한 실행경로·제약, 실제 사용 결과를 스스로 챙긴다. 사용자가 항목마다 다시 지시하도록 기다리지 않는다. 맡긴 범위 안의 설정/자료 등록과 검증은 책임부서에 정확히 배정하거나 짧은 본부 지침 정리로 마무리하고 본부 대화를 점유하며 기다리지 않는다.
단순 업무에는 최소한의 기존 코드/도구를 선택하고 확보한 자료를 재사용한다. 불필요한 스킬 동시 호출·새 모델 검증 세션을 만들지 않는다. 다음 실제 업무의 도구 사용 근거와 결과를 보고 적절히 선택했는지 확인한다. 스킬 이름을 직접 지시한 설치검증과 이름을 알려주지 않은 실제 업무의 자발적 선택을 구분하며 후자는 관찰 전 성공이라 하지 않는다.
아직 미연결인 도구는 사용 가능으로 표시하지 않고 필요한 사용자 인증/설치 단계만 알려준다. 외부 발신·새 비용·권한 변경·플랫폼 승인은 원래 범위를 지킨다. REA는 필요 시 검토, Perplexity는 보류라는 현재 결정을 유지한다.


## 복수 업무 대기열·완료 불명 처리 (2026-10-27 보완)

담당자별 미완료 접수는8개까지 보존하고 실제 실행은1개씩 created 순서로 전달한다. 정상 미전달 FIFO 업무는 보존한다. 완료 응답이 없다는 사실만으로 미실행으로 판단해 원래 지시를 재전송하지 않는다. 완료가 불명확하면 completion_unknown 확인 대기로 남기고 실제 대상의 효과와 최신 사용자 지시를 대조한다. 이전 v2의 최대1회 자동 이어가기 정책은 v3 소스에서 철회했다. 소스 저장과 서버 활성화는 별개이며 이번 관찰 시 서버는 여전히 v2였다.

부서별 실제 최신 입력 복구/고유 요청 경계와 전체 실행 경계의 미완료 범위는 docs/current-task-safety-2026-10-27.md를 따른다. 이 문서나 과거 배정 원문 자체로 업무를 재개하지 않는다.
