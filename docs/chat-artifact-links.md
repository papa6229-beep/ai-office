# 에이메스 채팅의 링크와 이미지·영상 자료

메인 채팅과 프로젝트 채팅은 `chat-message-content.js`의 작은 DOM 렌더러를 함께 사용한다. Markdown 링크·일반 http/https URL을 anchor로 표시하고, 이미지·영상 자료는 Office 내부의 기존 `workStageDialog`에 연다. 임의 HTML을 DOM에 삽입하거나 script를 실행하지 않는다. 본문 줄바꿈·코드·입력·기존 이력/동기화와 첨부 다운로드를 보존한다.

## 확인된 원인과 변경

기존 메인 답변은 workdesk.js에서 escape(content)만 사용하고 외부 동기화 때 textContent로 덮어썼다. 따라서 Codex 화면에서 Markdown이 보이는 것과 달리 Office에는 링크 요소가 없었다. 프로젝트 채팅에는 이미 project_panel_links의 안전한 parts와 opaque 로컬 파일 참조가 있어 이를 재사용했다.

- work_assistant._overview는 저장된 답변의 parts를 제공한다. 로컬 파일 참조는 assistant 답변에서만 등록한다. 사용자 메시지의 임의 경로를 다운로드 권한으로 바꾸지 않는다.
- 기존 project_panel_links는 Markdown 이미지와 확장자, 일반 Windows 절대경로를 구분하며 /C:/ 및 C:/ 경로의 기존 정규화를 사용한다. 코드 구간은 그대로 보존한다. 기존 project-panel-file route의 불투명 ref를 사용하고 URL로 드라이브 경로를 받는 API를 추가하지 않았다.
- 메인 최초 렌더와 외부 메시지 동기화가 같은 DOM 렌더러를 사용한다. 스트리밍 초안/이전 서버 응답의 웹 링크 fallback은 파일 접근을 등록하지 않는다. 프로젝트 채팅도 같은 표시를 사용한다.
- 첨부 이미지의 열기 버튼은 기존 확대 팝업을 사용한다. 프로젝트 첨부와 메인 첨부 다운로드 링크는 유지한다. 이미지는 img, 영상은 controls가 있는 video를 사용하며 HTML을 iframe/webview에 끼워 넣지 않는다.
- 외부 이미지는 클릭하기 전 자동 로딩하지 않는다. 내부 썸네일은 기존 attachment/media/agent-artifact/project-panel-file의 검증된 참조 URL만 사용한다. javascript:, data:, file: 등 실행 스킴은 웹 anchor로 만들지 않는다. 사용자명/비밀번호가 포함된 URL도 거절한다.

## 웹과 HTML

웹/HTML의 http/https 링크는 기존 target=_blank 경로를 사용한다. 전용 앱의 Program.External은 Office 원점(127.0.0.1:8765) 밖의 http/https를 Windows 기본 브라우저로 연다. 사용자 프로필이나 브라우저를 교체하지 않는다. 기존 시안의 127.0.0.1:50700/preview.html도 이 경로다. 일반 브라우저에서는 해당 확인 공간의 새 탭을 사용한다.

로컬 HTML에 이미 승인된 프리뷰 URL이 있으면 그 URL을 답변에 연결한다. 직접 Windows HTML 경로만 있는 경우 기존 opaque 파일 다운로드를 유지하며, 임의 HTML을 실행하는 새 서버 프리뷰를 만들지 않는다. 이는 실행 가능한 웹 프리뷰가 연결된 경우와 구별한다.

## 반영·확인 경계

새 JS/CSS는 기존 self_edit의 관리 원본 목록에 등록해야 제공된다. `already_applied` 변경 영수증만으로 정적 파일 제공 등록이 이루어지지는 않는다. 이 작업에서 최초404를 직접 확인하고 두 파일을 등록했다. index.html은 서버에서 workdesk.html을 삽입해 제공하므로 원본 바이트 동일성 대신 공용 모듈이 workdesk.js보다 앞에 있는지를 확인한다.

Python/Node 구문, 실제 서버 parts 응답·이미지 콘텐츠/해시·정적 파일 제공과 실제 UI 클릭은 각각 별도로 보고한다. 사용자 지침대로 테스트는 추가/실행하지 않는다. 사용자 브라우저/창을 가로채지 않고 별도 Ego 소유 공간에서 확인한다. 공간 종료/사용자 제어 중지는 즉시 따르며 같은 공간 재개에 사용자 지시가 필요하다. 파일·설정·메신저·모델을 바꾸거나 기록용 새 모델을 호출하지 않는다.

2026-10-26 실제 확인: 서버PID6084에 반영했다. 최초 확인 공간30 종료의 hard stop 뒤 대표의 확인 계속 지시를 받고 같은 공간을 다시 연결했다. 실제 과거 시안 답변의 메인 이미지 버튼과 프로젝트 답변의 이미지 버튼에서 모두 기존 팝업 열림 및 PNG764×1184 로딩을 확인했다. 기존 user 이미지 첨부164×204도 같은 팝업에서 열리고 다운로드 anchor를 보존했다. 프로젝트의 기존 Codex 열기와 링크/다운로드 표시도 유지됐다. 최소화된 Ego 창을 복원하지 않아 새 화면 캡처는 하지 못했다.

웹 링크 클릭은 올바른 URL/target=_blank로 표시되지만 Ego 소유 공간에서 popup 이벤트/새 탭이 관찰되지 않았다. 사용자 브라우저나 프로필로 우회해 재시도하지 않았다. 전용 앱의 기존 Program.External 경로는 소스로 확인했으며 사용자 앱을 새로고침한 뒤 실제 기본 브라우저 열기를 확인해야 한다. 링크 클릭의 전 구간이 실사용 검증됐다고 확대하지 않는다. 자세한 증거는 local_backups/chat-artifact-click-8d74addd/verification.json 및 manual-final.json에 있다.

## 2026-10-28 영상 재생 수정

작업창 요청 `02294b99bdeb448995c9e16724df9559`의 MP4가 Markdown의 `![]` 표기 때문에 이미지로 분류돼 깨진 img로 열렸다. 이제 MP4/M4V/WebM/OGV/MOV 확장자의 영상 분류를 이미지 표기보다 우선하며, 기존 메인·프로젝트 공용 렌더러에 ‘재생’ 버튼을 표시한다. 과거 서버 응답의 image=true도 실제 영상 경로로 구분한다. 영상은 사용자가 누른 뒤 기존 팝업의 video에서 로딩한다. 자동 재생·새 외부 창·영상 재생성은 추가하지 않았다.

기존 opaque 로컬 파일 참조는 유지한다. project-panel-file은 영상 MIME과 inline 응답, 단일 byte Range의 206/416 응답을 지원해 재생·구간 이동에 사용한다. 다운로드는 기존 attachment disposition을 유지하며 임의 경로 API나 HTML 실행 권한을 추가하지 않는다. 브라우저가 지원하지 않는 코덱은 팝업 안에 오류를 표시하고 원본 다운로드 경로를 유지한다.

실제 기존 ‘워터마크 없는 720 영상’ MP4(774059 bytes)를 Ego 공간5의 현재 Office 공용 렌더러/팝업에서 확인했다. 720×720, 5.208333초, 재생 시간 진행과 2.5초 이동, 실제 화면 픽셀을 관찰했다. 실제 기존 첨부 이미지도 1869×986으로 열렸고 다운로드 버튼을 보존했다. 확인 공간은 종료했다. 사용자 네이티브 앱 화면의 확인은 별개이며 1회 새로고침이 필요하다. 다른 코덱/형식 전체를 재생 검증했다고 주장하지 않는다. 근거는 `local_backups/office-video-playback-20261028/`다.
